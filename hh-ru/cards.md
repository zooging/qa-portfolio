# Карточки портфолио для hh.ru

Добавить 4 карточки в разделе «Портфолио» профиля. Ссылка в карточке — на GitHub-репозиторий; вторую ссылку (Allure) указать в описании.

## Карточка 1 — API-автотесты

**Название:** API-автотесты Restful Booker — 52 теста, pytest + requests, Allure, CI

**Ссылка:** https://github.com/zooging/qa-portfolio/tree/main/api-tests

**Описание:**
> Задача: покрыть API бронирований позитивными, негативными и контрактными сценариями. Написал 52 теста на pytest + requests, добавил JSON-схемы, генерацию данных и автоочистку, настроил GitHub Actions и Allure-отчёт. Результат: 35 passed, 17 xfailed на найденные дефекты, прогон 21 с, 9 баг-репортов. Отчёт: https://zooging.github.io/qa-portfolio/

## Карточка 2 — E2E на Playwright

**Название:** E2E-тесты SauceDemo на Playwright — 15 сценариев, CI, видео при падении

**Ссылка:** https://github.com/zooging/qa-portfolio/tree/main/e2e-playwright

**Описание:**
> Задача: автоматизировать ключевые пользовательские сценарии веб-приложения. Реализовал 15 E2E-тестов на Playwright: логин, каталог, сортировка, корзина, оформление заказа и негативные проверки. Использовал expect-assertions, трассировки и видео при падении; 15/15 passed за 7,7 с, CI на каждый push.

## Карточка 3 — Manual QA

**Название:** Manual QA-пакет по дипломному приложению — 30 кейсов, 50 проверок, 15 находок

**Ссылка:** https://github.com/zooging/qa-portfolio/tree/main/manual-qa

**Описание:**
> Задача: спроектировать документацию ручного тестирования для Flutter/Firebase-проекта аренды инвентаря. Подготовил тест-план, чек-лист на 50 проверок, 30 тест-кейсов, трассировку на 16 требований и 15 баг-репортов (10 подтверждены ссылками на код). Отчёт содержит остаточные риски и план прогона на эмуляторе.

## Карточка 4 — Нагрузочное тестирование

**Название:** Нагрузочный smoke-тест k6 — p95 181 мс, обнаружено ограничение API

**Ссылка:** https://github.com/zooging/qa-portfolio/tree/main/load-tests

**Описание:**
> Задача: оценить время отклика и поведение API под небольшой нагрузкой. Написал сценарий k6 с ramp-up до 3 VU и порогами p(95) < 2 с и error rate < 1%. Результат: 123/123 проверок, p95 = 181 мс; обнаружено, что публичный стенд отвечает 418 уже при 2–3 VU — ограничение вынесено в отдельную метрику.
